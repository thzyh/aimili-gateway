# ny 出口 1、2 客户端真连接延迟排查

## 故障与验证结果

时间为北京时间 2026-11-17。v2rayN 7.25.4 使用本机 Xray 26.9.9，截图显示 20:08 测试 ny 分组，出口 1、2 为 `-1`。实际测速配置为 `ny.zouyunhui.cc.cd` 上的 TCP/Vision + REALITY，五个端口依次为 `8443`、`20000`–`20003`，目标为 `https://www.google.com/generate_204`。客户端和服务端的身份、SNI、公开参数已按端口匹配；没有输出凭据。

| 对照 | 出口 1 | 出口 2 |
| --- | --- | --- |
| 20:07，Gateway 手动检查 | 本机协议和出口检测成功 | 本机协议和出口检测成功 |
| 20:17，ny 经真实 SOCKS 隧道请求相同目标 | `17928`，3/3 HTTP 204 | `17929`，3/3 HTTP 204 |
| 20:17–18，Windows 隔离 Xray，原订阅配置 | `20000`，0/3 | `20001`，0/3 |
| 20:21–22，Windows 通过以太网直接拨 TCP | `20000`，0/6 | `20001`，0/6 |
| 20:20，Windows 隔离 Xray，经临时 SSH 转发到原入站 | 2/2 HTTP 204 | 2/2 HTTP 204 |

- 首次可核实的失败发生在公网 TCP 握手。VPS `eth0` 上有本机发来的 `SYN`，有 VPS 发出的 `SYN-ACK`，但没有收到最后一个 `ACK`；同轮 `20002/20003` 可完成握手。失败请求还没进入 REALITY 认证与 OpenVPN 数据链路。仅凭服务器抓包，不能确定握手回包在 Windows、局域网设备或公网路径的哪一段被丢弃。
- Gateway 检测走 VPS 回环入站和本地隧道；它显示“本机检测成功”符合测量范围。20:08:40 的个别 DNS 超时对应主连接 `tun0`，不是出口 1 的 `tun120` 或出口 2 的 `tun138`。20:03:49 v2rayN 有一条测速异常但无端口归属；不运行 v2rayN 的裸 TCP 测试已能复现本次两端口失败。
- 改用已允许但未占用的端口，用限时、限当前来源的 TCP 诊断转发透传时，REALITY 仍由原入站处理。20:26–27，`20006 → 20000` 和 `20007 → 20001` 各两次通过原 Google HTTP 204 目标，随后分别从 `api.ipify.org` 返回原出口 IP `180.27.15.79` 和 `123.1.102.46`。另两条备选端口 `20004/20005` 曾出现个别超时。换端口可绕过已复现的公网入口故障，不能当作上游网络永久修复。

## 安全恢复路径

- 如需立即绕行，可在本机运行 `ssh -NT -o ExitOnForwardFailure=yes -L 127.0.0.1:22000:127.0.0.1:20000 -L 127.0.0.1:22001:127.0.0.1:20001 ny`。在 v2rayN 中复制原出口 1、2，副本的地址改成 `127.0.0.1`，端口分别改成 `22000`、`22001`，保持 REALITY 的 SNI、公钥、Short ID 和流控等参数原样。只检测副本即可，活动节点无需改动。终端需在使用副本期间保持运行。
- 单独增加转发不会更改 3x-ui 发布的订阅。永久入口和订阅同步结果见下文，原 Xray 监听仍保留。

## 已部署的公网备用入口

- 用户授权后，20:33 在 ny 启用 `20006 → 20000`、`20007 → 20001` 的 IPv4 TCP 转发。仅匹配 `eth0` 上发往 ny 公网 IPv4 的对应端口；原防火墙放行范围、Xray 认证、所属 OpenVPN 隧道、原订阅和原监听不变。
- 内核 `nftables` 只加载独立的 `ip aimili_ny_public_alias` 表。`/etc/ufw/aimili-ny-public-alias.nft` 保存规则，已启用的 UFW 由 `/etc/ufw/after.init` 在启动时加载。规则静态检查和隔离网络命名空间加载通过；实际启动钩子连续执行两次仍只保留两条规则。未重启 VPS、未重载整个防火墙。扩容并分配新的原生入口前，需保留这两个端口或先移除备用映射。
- 20:34 从 Windows 用原 v2rayN 测速配置，隔离启动相同 Xray/SOCKS5，备用端口 `20006` 和 `20007` 对原目标分别返回 4/5、5/5 次 HTTP 204。两条路径分别得到原出口 IP `180.27.15.79`、`123.1.102.46`；主连接和出口 3、4 的同轮对照返回 204。公网备用入口绕过原握手故障，但仍可能遇到公网瞬时超时。
- 上线后三轮裸 TCP，两条备用端口均为 3/3 成功，原端口均为 0/3。20:36–37 再以 [v2rayN 7.25.4 的同一 SOCKS5/HTTP 双样本逻辑](https://github.com/2dust/v2rayN/blob/7.25.4/v2rayN/ServiceLib/Handler/ConnectionHandler.cs) 和 [5 秒总预算](https://github.com/2dust/v2rayN/blob/7.25.4/v2rayN/ServiceLib/Global.cs) 隔离复测：原端口均 0/4，`20006` 为 2/4、`20007` 为 4/4，`8443` 对照为 2/4。`20006` 有一轮第一条已获 HTTP 204（4744 ms），第二条失败后整轮仍为 `-1`；另一轮确实未在预算内取得响应。此结果不等于已在 v2rayN 界面重测或完全消除 `-1`。
- 此阶段未变更原订阅和客户端配置。20:49 本机 v2rayN 生成的测速配置仍指向 `20000/20001`；有备用入口但未让原操作使用它，是两条节点仍持续显示 `-1` 的原因。

## 原订阅和客户端已同步

- 使用 [3x-ui Hosts API](https://github.com/MHSanaei/3x-ui/blob/main/docs/content/docs/en/reference/api/hosts.mdx) 对两条 Gateway 受管 TCP/Vision 入站分别设置订阅发布端口 `20006`、`20007`。同一条订阅 URL 实测返回 `8443, 20006, 20007, 20002, 20003`；五条节点的名称、身份和 REALITY 参数逐项比对一致。原 Xray 配置摘要、服务进程和出口隧道不变。这个设置只改变订阅发布入口；如果未来把这两条入站改为 UDP/Hysteria2，须先调整或移除对应 Host 覆盖和 TCP 转发。
- 本机 v2rayN 的 `ny` 自动订阅更新未启用。读取并核对原订阅后，只同步本机 SQLite 内两条非活动节点的端口，保留节点索引和参数，未修改测速结果、活动主连接或系统代理。原客户端和核心进程保持运行。按 [v2rayN 7.25.4 测速代码](https://github.com/2dust/v2rayN/blob/7.25.4/v2rayN/ServiceLib/Services/SpeedtestService.cs)，真连接测试以节点索引重新读取已保存的配置。
- 21:03 左右，Windows 上两条新端口均完成 TCP 握手，旧端口同轮均失败。隔离启动 v2rayN 使用的 Xray，核对配置与本机持久记录一致，用真实代理访问 IP 查询服务，五条均返回各自的出口；出口 1 为 `180.27.15.79`，出口 2 为 `123.1.102.46`。同一时段在 ny 直接经 `17928/17929` 请求原 Google 目标，分别 3/3 HTTP 204。
- Windows 使用原生 5 秒双请求规则复测，首批四轮出口 1 为 1/4，出口 2 为 3/4；再次交叉复测，分别为 3/4 和 4/4。21:07 有一轮出口 1 首次已返回 HTTP 204（4.824 秒），原逻辑仍报 `-1`；出口 4 同轮两次均返回 204（4.349 秒加 0.473 秒），仍在第二次请求之后的等待超时。均有原始样本证明客户端会丢掉成功结果。另有出口 1 的轮次没有成功样本，不能视作误报。将目标换为 gstatic 或 Cloudflare 的短响应接口也未稳定改善。
- 服务端对应记录确认出口 1、2 分别仍由 `tun120`、`tun138` 提供。21:02:48 有一条出口 1 的单次 DNS 服务器超时，未记录具体查询域名，不能据此归因整轮测速。生产服务未重启，ny HTTPS 首页返回 HTTP 200。

## 客户端测速修正的隔离验收

- 对 v2rayN 7.25.4 准备了独立源码补丁：两次请求各有原来的 5 秒超时，收到 2xx 就保留该样本，只有两次都没有成功才返回 `-1`；用户取消测试仍立即生效。两次合计最多约 10.1 秒。补丁针对原版源码检查可应用，并提取实际方法编译为独立命令行程序；未替换正在运行的 v2rayN。
- 本地回归覆盖首次 204、随后超时，首次超时、随后 204，两个 503 和主动取消，全部符合预期。21:10 再用本机持久配置、相同 Xray 和同一 Google 目标执行四轮，五条出口合计 20/20 返回真实延迟。出口 1 四轮为 `441/1183/1066/698 ms`，出口 2 为 `448/2600/497/444 ms`。ny 公网端口同时观察到握手完成及双向数据。该验收覆盖测速链路和源码补丁，未在原版桌面窗口运行新逻辑，也不代表长期公网不会超时。
