# ny 首次部署普通出口无法补齐

## 已确认原因

目标为 `ssh ny`、`ny.zouyunhui.cc.cd`。2026-11-01 17:29–17:49（北京时间）一键安装在出口验收阶段耗尽 1200 秒预算，主连接正常、普通出口仅 1/4 就绪，尚未进入 Gateway 安装阶段。

这不是根据超时推测网络问题：现场控制 API、节点数据和日志给出了以下对应证据。

- `ui_auth.json` 没有 `exit_slot_residential_only`，旧 `get_exit_slot_config()` 缺省为 `True`；出口 2–4 的持久化状态明确为“暂无可用住宅节点”。读取时的 10 个有效缓存均为 `hosting`，主连接和备用则允许使用机房节点。
- 五个目标的专属备用均 `ready/egress_ok=true`，包含三个空出口的备用。旧 supervisor 对没有活动身份的空出口只调用 `pick_slot_node()`，不会提升自己的备用；已有身份发生故障时才有提升分支。这是初始化路径与故障恢复路径不一致。
- 出口 1 的候选在 17:43:51 报 `AUTH_FAILED`，随后该出口通过故障恢复提升机房备用；其运行状态明确写“已切换到专属备用”。这解释了为何最终是 1/4 而不是 0/4：它进入了已有故障恢复分支，其他三个空位仍停在初始化过滤分支。该候选的认证失败不是其他三个空位长期等待的共同原因。
- 17:31:22 首轮检测了 9 个候选、保留 5 个有效节点，停止原因为 `batch_budget`；下一轮直到 17:41:33 才启动。两分钟的有界扫描后睡十分钟，本轮 20 分钟安装窗口内只执行两批探测，放大了供给缺口。
- 控制 API 的 `candidates` 排除了已使用、保留及出口 IP 冲突的节点；`capacity.currentValidNodeCount=10` 而候选列表为 0。因此旧日志中的“候选池 0”不是所有有效节点都消失。
- 可用内存约 175 MiB、磁盘可用约 5 GiB；主连接、一个普通出口和五个备用均已真实出网，没有本次资源耗尽的直接证据。BBR 步骤已经成功，不能据安装超时将其认定为原因。

`residential_only=True` 的默认行为由整合提交 `7eeaf43c` 带入；`batch_budget` 后进入普通长退避的路径可追溯到 `b2b8cae2`。这次是新部署数据缺省触发的既有代码问题，不是新增 BBR 步骤引入的回归。

现场签名包为 `project-v0.2.45-vps`，业务提交 `0c0fe263106c5a7ac4e2b531145211e15318287f`。运行文件与该包的 manager 摘要一致，没有把本地未发布代码误认为已在 VPS 生效。

## 修复

- 普通出口未配置限制时默认住宅优先、机房兜底；排序优先住宅，不仅放宽过滤。明确保存的“仅住宅”、国家、运营商、类型和固定候选仍受约束。
- 空出口在冷拨号前检查自己的专属备用；复用现有提升逻辑和真实健康验证，不复制其他出口的连接，也不绕过显式筛选。
- 分批扫描因为批次预算停止、且仍缺活动出口时，使用已有短退避续检；资源压力、维护冲突和平稳期保留原退避。探测预算与并发资源保护保持有效。
- 安装器为缺少策略字段的新建/中断部署补齐默认值，不覆盖显式配置。进度与最终超时信息区分有效缓存、未占用候选、就绪备用、类型策略和缺失出口编号。
- 发布预检另确认本机构建目录的 3x-ui 产物与固定 Release 资产不是同一字节文件。构建器增加 `-XUIBinary` 和固定摘要前置校验，使用已核对的 `v0.2.5-vps` 缓存，避免签名清单引用旧 URL 却写入另一个二进制的摘要。
