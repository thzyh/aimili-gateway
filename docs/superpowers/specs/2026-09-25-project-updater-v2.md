# 项目更新器 v2 设计与验收

## 目标

首次一键部署即安装独立的可信更新入口。以后每个正式版本由“检测 → 确认 → 下载/备份/安装/核验”完成。旧更新器遇到更新协议变化时，先从签名发布包升级自身，再继续同一事务。任何不能安全自动完成的场景都要在停服前报告具体阻止项与升级路径。

## 信任与权限

- 保留固定的 Ed25519 信任公钥、GitHub 固定仓库和签名清单 v1 外壳。外壳只描述版本、摘要、最低更新器版本和资产；未来的安装契约可独立升级。
- 低权限 fetcher 只联网下载；root 服务只读取已复制到 root 私有目录且重新验签的资产，继续限制为回环网络。安装动作取固定类型和固定目标清单，不执行任意发布脚本。
- 固定入口 `project_update.py` 最终由小型引导器占用。引导器从 root 所有、不可由 fetcher 修改的两槽目录读取当前/上一更新引擎，校验 SHA256 后运行。新引擎异常退出时自动切回上一槽；涉及已开始的生产变更时，先走恢复事务，无法确认恢复就保持 `repair_required`，不再次执行 apply。
- 从 v0.2.13 升级到首个 v2 过渡版本时，v1 安装器照常应用已签名的契约 1 包。过渡版本的引擎在下一次 root timer 调用中，将同一已验签包中的引导器和自身安装到两槽，再原子切换固定入口。之后新安装协议用“先升级引擎 → 同一 runId 续作”的两阶段事务。
- 旧引擎只认 `vX.Y.Z-vps` Release 标签，永久保留一个安全过渡版；后续正式项目发布使用 `project-vX.Y.Z-vps` 标签，清单里的语义版本仍为 `vX.Y.Z-vps`。新引擎识别两类标签。旧机无论何时检测，先看到兼容的过渡版，避免跳过更新引擎直接安装未来协议。

## 兼容与执行

- 签名清单声明平台、布局版本、最低/最高更新器版本、数据库模式范围、空间需求，以及 Gateway、egress、3x-ui、Xray、Caddy、OpenVPN、systemd 等组件的版本与变更类型。未知字段和未知变更类型在停服前拒绝。
- 检测返回版本、是否可自动升级、阻止原因代码、受影响组件及明确升级路径。仓库文档路径由本地错误映射提供，不信任发布包中的任意 URL。
- 固定组件执行器按依赖顺序预检、备份和替换。Caddy 配置先验证，Xray 配置先测试，systemd unit 先检查；数据库迁移在副本上验证。不可逆迁移或现有资源不属于 `agw-` 时阻止自动安装。
- 更新前记录目标组件和连接身份摘要。更新后同时验证服务健康、Gateway API、订阅、主连接及已有出口的真实数据面。失败恢复程序、配置和 SQLite 快照，并核对身份。不能确认恢复时锁住新事务。
- 下载/安装/重启/恢复进度和诊断写到 root 可信结果。Gateway 网页读取这些结果；断线、Gateway 重启或浏览器刷新后续查同一 runId。

## 发布与验收门禁

- 用可移植构建脚本在 CI 生成可复现的完整资产，签名密钥不进入仓库或 VPS。先上传全部资产并验证摘要，再发布稳定频道；目标版本固定到 tag 与摘要。
- 测试矩阵含 v0.2.13 过渡升级、引擎自身升级与坏引擎回退、环境不兼容、磁盘不足、证书/签名错误、断电续作、数据库恢复、全组件测试 VPS。每个阻止项均验证页面理由与升级路径。
- 在 bj 等测试 VPS 上先验收，再让用户通过网页更新 jjs；xjp 保留历史环境直至单独验证。用户执行正式更新前，不以本地模拟测试冒充生产验收。

## 物理边界

目标是“支持矩阵内无需再部署更新功能补丁”。操作系统失效、信任根丢失、磁盘不足、不可逆数据库变更、用户资源冲突等无法承诺无条件成功；必须在变更前给出具体阻止原因与可执行的恢复/迁移路径。
