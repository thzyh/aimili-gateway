# 运行节点稳定排序、切换故障修复与两层节点池设计

日期：2026-08-31

状态：已批准

## 1. 目标

本增量在不增加 AimiliVPN 实际运行出口数量的前提下，完成三项改进：

1. Gateway 页面固定显示顺序为“主连接 → 出口1 → 出口2 → 出口3”，并显示每个运行出口的公网端口与 mixed 端口。
2. 修复出口 IP 或公网协议切换后出现的延迟 `-1`、`repair_required` 和 AimiliVPN/Xray/Gateway 状态分叉。
3. 把 VPNGate 官方国家目录与已验证有效节点缓存拆成两层，建立固定 30 条缓存、国家覆盖、保护与持久化规则。

本设计不得恢复 `21000`、balancer 或额外长期并存的公网入站，不得增加主连接加三个普通出口之外的运行出口。

## 2. 调查事实与根因

### 2.1 本地与远程基线

- Gateway 功能分支：`feat/main-switch-protocol-modes`，调查时提交 `78447e0`，与远程一致，工作树干净。
- AimiliVPN 功能分支：`feat/main-switch-protocol-modes`，调查时提交 `2cada1f`，与远程一致，工作树干净。
- Gateway `main`：`1eb90cb`，与 `origin/main` 一致。
- 生产仍使用主连接加三个普通出口、四个公网入站、四个 mixed 和一个 Xray 进程。

### 2.2 客户端与生产状态并非同一故障视图

本机 v2rayN 最新数据库记录显示，当次测试不是四条全部失败：

| 逻辑出口 | 公网端口 | 协议 | 当次延迟 |
| --- | ---: | --- | ---: |
| 主连接 | 8443 | TCP/Vision | 478 ms |
| 出口1 | 20000 | Hysteria2 | -1 |
| 出口2 | 20001 | Hysteria2 | 465 ms |
| 出口3 | 20002 | XHTTP | -1 |

Gateway 数据库同时把主连接与出口2标记为 `repair_required / rollback_failed`。页面中四条运行记录内部仍会受国家、延迟和更新时间排序影响，因此“第几行”不能可靠表示逻辑出口，这也是用户看到的名称与 v2rayN 端口结果不一致的重要原因。

### 2.3 第一处明确失败边界

第一处可证实的系统失败位于 AimiliVPN 本地代理与进程资源边界：

- `aimilivpn.service` 的 `TasksMax` 为 48。
- `proxy_server.py` 默认允许 256 个全局线程式代理连接。
- 故障时间窗内记录到至少 189 次来自回环地址的连接因全局代理上限而被拒绝，说明重试流量来自本机 Xray，而不是公网直接访问本地代理。
- 2026-08-31 05:30:28 UTC，AimiliVPN 已创建槽位 OpenVPN 子进程，随后在创建日志读取线程时抛出 `RuntimeError: can't start new thread`。
- 异常发生在子进程创建之后，现有代码没有在该异常路径回收子进程。该进程继续占用 `tun122`，但没有进入 `exit_slots` 内存状态。
- 后续维护把槽位视为 pending 并重复拨号，持续收到 `Device or resource busy`，形成 AimiliVPN 运行进程、持久状态和 Gateway 状态三方分叉。

因此单一根因是：本地代理并发模型允许消耗的线程数超过 systemd 任务预算，并且线程创建失败后的 OpenVPN 子进程清理不完整。失效节点或协议重试是触发条件；订阅格式、UUID、Hysteria2 Auth、REALITY/XHTTP 参数和 Xray 全局重载不是第一失败边界。

## 3. 总体架构

采用“确定性有效缓存＋每出口容量隔离＋严格状态收敛”的方案。

```text
VPNGate 官方目录层
  └─ 国家、官方候选数、观测时间
          │ 单国或全量抓取
          ▼
探测与标准化
  ├─ 住宅优先
  ├─ 住宅失败回退机房
  └─ 失败节点不进入有效缓存
          │
          ▼
30 条已验证有效缓存
  ├─ 运行/事务硬保护
  ├─ 国家锚点
  ├─ 本轮手动刷新保护
  └─ 旧健康 → 新住宅 → 新机房 → 质量补满
          │
          ▼
主连接 + 出口1 + 出口2 + 出口3
  └─ 每出口独立公网协议，mixed 不变
```

官方目录层只保存安全统计；有效缓存层继续使用 `nodes.json` 保存现有节点材料。刷新摘要与保护轮次写入新的 `pool_metadata.json`，不得保存密码、Cookie、UUID、Auth、私钥、随机后台路径或订阅地址。

## 4. Gateway 页面与固定顺序

### 4.1 稳定排序键

运行节点在任何筛选和排序方式下都先组成独立分区：

| 类型 | 稳定顺序键 |
| --- | ---: |
| 主连接 | 0 |
| 出口1 | 1 |
| 出口2 | 2 |
| 出口3 | 3 |

候选节点从键 100 开始，再应用用户选择的国家、类型、延迟或更新时间排序。国家、IP、协议、状态、延迟和刷新时间不得改变四个运行节点之间的相对顺序。

运行节点仍遵守“始终显示”的现有行为；筛选只影响非运行候选。

### 4.2 端口展示

表格增加“端口”列，运行节点显示：

- 公网：`publicPort`，兼容旧响应时回退 `vlessPort`。
- mixed：`mixedPort`。

非运行候选显示 `—`。公网协议切换只改变公网协议，不改变这两个逻辑端口。

### 4.3 两个国家入口

页面把现有单一国家选择拆成：

1. “只看现有国家”：来源为当前有效缓存和运行节点，只负责筛选。
2. “手动补充国家”：来源为官方国家目录，用于触发单国抓取、探测和重平衡。

页面同时显示：

- 官方候选节点数；
- 当前有效节点数；
- 当前有效国家数；
- 最后刷新国家、结果、有效数、完成时间；
- 刷新失败时的安全错误码。

## 5. 本地代理容量与异常隔离

### 5.1 容量预算

现有四个逻辑出口共用一个 256 许可量的全局信号量，不能满足受控的 systemd 任务边界。新模型使用两级许可。2026-09-04 根据真实客户端并发复核后，生产容量修订为：

- 全局代理连接上限默认 128；
- 每个监听实例上限默认 64；
- 环境变量只能在安全闭集内调小或显式配置，生产部署固定为上述值；
- `TasksMax=160`，为基础线程、控制 API、四个 OpenVPN 进程、维护线程和短时子进程保留余量；
- `MemoryHigh=180M`、`MemoryMax=220M` 和每出口独立监听隔离保持不变。

某个坏出口最多占用自己的 6 个代理线程，不得阻塞其他三个出口或控制路径。

### 5.2 接入失败处理

代理接受连接的顺序为：

1. 获取监听实例许可；
2. 获取全局许可；
3. 创建工作线程；
4. 工作线程结束后释放两级许可。

任一步失败都必须关闭客户端并释放已获取许可。`threading.Thread.start()` 抛出异常时不得泄漏 socket 或许可，也不得让代理监听线程退出。

### 5.3 OpenVPN 子进程事务

`run_openvpn_until_ready` 必须把“启动子进程、启动日志线程、握手、策略路由、登记运行状态”视为一个本级事务：

1. 子进程启动后，只要日志线程创建、握手或策略路由任一步失败，立即终止并等待子进程退出。
2. `setup_policy_routing` 返回显式成功/失败；三次失败后不得继续把槽位写成 up。
3. 只有 OpenVPN 握手成功、策略路由存在、本地代理已监听时，才把进程放入 `exit_slots`。
4. 在同一槽位重新拨号前，按精确 `AIMILI_SLOT` 标记检查受管 OpenVPN 进程；发现未登记的同槽位进程时只回收该受管进程，不扫描或删除无关 VPN 进程。
5. 失败后写入 pending，并使用有界退避；不得每个维护周期持续刷相同错误。

## 6. Gateway、AimiliVPN 与 Xray 状态收敛

### 6.1 切换前置门

出口协议切换前必须确认：

- AimiliVPN 返回同一槽位和候选身份；
- 槽位状态为 up；
- mixed 本地代理真实出站可用；
- 当前 Gateway 绑定与 AimiliVPN 身份一致。

任一条件失败时不得修改 3x-ui/Xray 入站，直接把目标出口标记为 degraded 或 `repair_required`，并返回单一安全错误码。

### 6.2 切换与回滚

协议切换继续使用现有每出口单协议事务：

1. 快照目标受管入站和协议状态；
2. Xray 离线校验；
3. 原位热替换目标入站；
4. 验证目标公网协议、mixed 和真实出口；
5. 验证其他三个出口仍可用；
6. 提交协议状态与订阅；
7. 失败仅回滚目标出口。

回滚后必须重新读取 AimiliVPN 身份和 Xray 入站。如果恢复状态与快照不一致，保留 `repair_required`，不得把数据库强制改成 ready。

### 6.3 周期检查

Gateway 的 check 结果必须同时反映 AimiliVPN 和公网协议：

- AimiliVPN pending/down 或身份不一致时，Gateway 不能保持 ready。
- AimiliVPN 有未登记的受管进程时，先由 AimiliVPN 收敛或回收，Gateway 不直接改其状态文件。
- 订阅只发布已提交协议模式；`switching`、`rolling_back` 和 `repair_required` 不得发布未提交的新材料。

## 7. 两层节点池与确定性重平衡

### 7.1 固定容量

有效缓存硬上限为 30。`MAX_FETCH_ROWS` 仍表示官方候选扫描量，不是有效缓存容量。

旧的 `TARGET_VALID_POOL_SIZE` 环境变量不再允许把缓存扩大到 30 以上；兼容读取时将值收敛到固定上限。

### 7.2 节点集合

重平衡器只接受真实探测为 available 的节点，以及当前必须保留但需要明确显示异常的运行/事务节点。普通 unavailable、untested 和全部探测失败国家不占有效名额。

### 7.3 选择优先级

`rebalance_valid_pool` 使用确定性顺序：

1. 硬保护：当前主、三个运行槽位、主事务旧/新候选和其他正式 reserved 候选；
2. 本轮手动刷新成功节点；
3. 国家锚点：每个已选且真实 available 的国家至少一条；
4. 旧健康节点；
5. 新住宅/mobile 节点；
6. 新机房/hosting 节点；
7. 延迟、质量分、最近成功时间和稳定 ID 排序补至 30。

同一优先级内使用稳定比较键，输入顺序变化不得造成无意义抖动。

“每国至少一条”指当前纳入有效缓存且探测成功的国家。若真实可用国家超过 30，按硬保护、最近手动补充、旧国家覆盖和最高质量选出最多 30 个国家；固定容量优先级高于无限国家覆盖。

### 7.4 手动刷新保护

一次单国刷新成功后：

- 至少一条该国成功节点进入缓存；
- 成功节点保护到下一次普通维护成功完成；
- 单国刷新不删除其他国家；
- 合并后立即全局重平衡；
- 如果连续手动补充超过容量，最新成功国家优先，最旧且非运行的手动保护可提前结束，但运行节点永不因此被淘汰。

### 7.5 住宅回退

单国候选按住宅/mobile 优先探测。住宅候选未达到一条成功时继续探测同国机房/hosting 候选；只要机房成功，该国可进入有效缓存。全部候选失败时记录失败摘要，但该国不占缓存名额。

### 7.6 持久化

`nodes.json` 继续保存有效节点；`pool_metadata.json` 原子写入以下安全数据：

- schema 版本；
- 普通维护轮次；
- 本轮手动刷新保护 ID 与过期轮次；
- 官方国家和候选计数、观测时间；
- 最后全量/单国刷新结果、计数、时间和安全错误码。

进程重启后读取并校验两个文件，再执行一次只读式重平衡。文件损坏时保留可验证的旧 `nodes.json`，元数据回到安全默认值，不清空节点池。

## 8. API 变化

现有接口保持兼容，并扩展安全字段：

- 国家目录响应增加官方候选总数、当前有效总数、当前有效国家数和观测时间。
- 单国刷新状态增加持久化的最后结果、完成时间、缓存总数和国家有效数。
- 候选/运行节点响应继续返回 `publicPort` 与 `mixedPort`；前端兼容旧 `vlessPort`。

不增加返回 OpenVPN 配置正文、认证材料或订阅正文的新接口。

## 9. 测试策略

### 9.1 AimiliVPN 单元测试

- 全局和每监听实例许可隔离；一个监听耗尽不影响其他监听。
- 工作线程创建失败时关闭 socket 并释放两级许可。
- OpenVPN 日志线程创建失败时子进程被终止且不进入运行状态。
- 策略路由失败时子进程被回收、槽位为 pending。
- 未登记同槽位受管进程被精确回收，其他槽位和非 Aimili 进程不受影响。
- 30 条硬上限、国家锚点、旧健康优先、住宅回退机房、运行节点保护和手动刷新保护。
- 单国刷新保留其他国家并立即重平衡。
- 元数据原子持久化和损坏恢复。

### 9.2 Gateway 与前端测试

- 所有国家、协议、延迟、状态和更新时间排序下，四个运行节点顺序恒定。
- 公网/mixed 端口正确展示，候选显示空值。
- 两个国家入口数据源互不混用。
- AimiliVPN pending/down 时协议切换在修改 Xray 前失败。
- 切换后非目标出口不变，订阅只包含已提交模式。

### 9.3 集成与生产验证

- 本地全量 Go、Python、Vitest、前端构建和补丁检查。
- 故障注入重现 `can't start new thread`，确认无孤儿 OpenVPN 和 TUN 占用。
- 生产先备份，再部署 AimiliVPN 修复并重启一次，使四槽位从正式状态重建。
- 通过 Gateway 正式 check/repair 路径收敛主连接和三个普通出口，不直接编辑数据库。
- 按当前已提交协议模式逐条验证 TCP、XHTTP、Hysteria2、mixed、代理 DNS和真实出口。
- v2rayN 7.24.4 刷新统一订阅后逐条延迟与连接验证。
- 重启 AimiliVPN、Gateway 和 x-ui/Xray 后复验。
- 至少 300 秒观察线程数、任务数、内存、Swap、单 Xray PID、四服务和错误日志。

## 10. 阶梯部署与回滚

1. Stage 0：只读预检、数据库/配置/三文件备份、记录非 Gateway 资源指纹。
2. Stage 1：部署 AimiliVPN 容量、进程清理和节点池代码；重启 AimiliVPN，验证四个本地代理和槽位身份。
3. Stage 2：部署 Gateway API 与状态收敛；只通过正式 check/repair 恢复状态。
4. Stage 3：部署前端固定顺序、端口和两层国家界面。
5. Stage 4：刷新订阅并从外部逐条验证四公网协议和四个 mixed。
6. Stage 5：重启恢复和 300 秒资源观察。

每一级失败只回滚该级。不得删除或修改非 Gateway 受管 3x-ui 资源，不得增加运行出口、公网入站或 mixed 数量。

## 11. 完成标准

- 页面始终按主连接、出口1、出口2、出口3显示并包含两类端口。
- 切换一个出口不会耗尽全局任务，也不会改变其他出口、mixed 或协议。
- 任意线程/子进程/策略路由失败均无孤儿 OpenVPN 和 TUN。
- Gateway、AimiliVPN、Xray 和订阅对四个逻辑出口状态一致。
- 有效缓存始终不超过 30，当前纳入且真实可用的国家保留锚点。
- 单国刷新、住宅回退、保护规则和重启持久化均有自动化与生产证据。
- v2rayN 四条节点不再因本次资源级联故障出现 `-1`。
- 生产仍为四个 AimiliVPN 运行出口、四个公网入站、四个 mixed 和单 Xray。
