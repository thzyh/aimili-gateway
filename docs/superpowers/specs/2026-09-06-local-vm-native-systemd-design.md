# 本机 VMware Ubuntu 原生 systemd 部署设计

日期：2026-09-06（Asia/Shanghai）。状态：已批准，进入实施。

## 目标

在现有 VMware Ubuntu 虚拟机中部署一套与 ny 完全隔离的 Aimili Gateway 本机环境。AimiliVPN、3x-ui/Xray、Aimili Gateway 和 Caddy 均以 Linux 原生 systemd 服务运行；本机不保留 Docker 备用方案。

首期交付主连接、出口1、出口2、出口3共四个逻辑出口。首期预计运行四个 OpenVPN 进程和一个 Xray 进程，但这些数字只是当前部署清单的期望值，不是架构硬上限。

## 已有基础与边界

- 复用 `D:\VirtualMachines\AimiliGatewayLocal` 中的现有 VM、24 GiB 动态磁盘、固定 Ubuntu OVA、NoCloud seed、SSH 密钥和桥接网络。
- VM 固定使用 2 vCPU、2048 MiB 内存和约 1 GiB swap；本轮不自动扩容。
- 宿主可用内存低于 3.5 GiB 时拒绝自动启动 VM，不结束用户程序。
- VM 只有一张连接 VMnet0 的物理桥接网卡，承担默认路由和管理流量。
- UFW 管理入口只允许创建 VM 时记录的 Windows 物理地址；不增加路由器端口转发，不开放无来源限制的公网代理。
- 不连接 ny，不读取或复制 ny 的数据库、配置、证书、Cookie、token、UUID、私钥、公网地址或后台路径。
- 不读取或修改 v2rayN 配置、日志、活动节点、TUN 或系统代理；只读取 PID、系统代理和 Windows 默认路由摘要验证不变性。
- 不修改 Windows 默认路由、DNS 或防火墙，不使用浏览器自动化；页面、订阅和 v2rayN 最终验收由用户执行。

## 方案选择

采用“复用现有原生安装器和运行模型，加一层本机薄编排”。AimiliVPN 复用当前仓库的 Linux 安装器与 systemd 模型；Gateway 复用既有二进制、配置、systemd 单元、账户工具和验证脚本；3x-ui/Xray 与 Caddy 复用项目已经验证的原生版本和配置结构。

不复制 ny 的在线环境，也不把远程部署脚本原样套到本机。薄编排层只负责固定本机来源、构建与上传本机提交、生成独立凭据、安装、状态、备份、回滚和脱敏验证。

## 组件与职责

### Windows VM 编排

`deploy/local-vm` 是本机部署唯一入口。它负责：

- 宿主资源和不变性安全门；
- VM 生命周期、SSH 主机密钥固定和可达性；
- 来宾出网、资源、UFW 和服务状态检查；
- 将本机工作树构建产物传入 VM；
- 按阶段调用来宾原生安装脚本；
- 生成脱敏状态和验收报告。

脚本不打印完整 IP、MAC、Windows 用户名、密钥路径或任何凭据。

### AimiliVPN

AimiliVPN 作为 `aimilivpn.service` 运行，拥有 OpenVPN、TUN 和策略路由所需权限。主代理、控制 API 和多出口代理只监听回环地址，供 Gateway 和 Xray 使用。

首期配置三个多出口槽位，加上主连接形成四个逻辑出口。槽位数量由部署清单和现有 `MULTI_EXIT_SLOTS`、`MAX_EXIT_SLOTS` 等配置表达；状态脚本从运行数据发现槽位，不把三个槽位写死为永久限制。

### 3x-ui/Xray

3x-ui 作为 `x-ui.service` 运行并管理 Xray。首期只部署一个 Xray 进程，由现有受管资源模型提供主连接和三个出口的公网协议入口。

本轮不建设多 Xray 实例编排，但所有状态字段使用实际进程数和部署清单期望值，不能写成“系统永远只能有一个 Xray”。未来改变 Xray 实例数属于独立容量和端口设计，不需要推翻本机原生部署基础。

### Aimili Gateway

Gateway 作为 `aimili-gateway.service` 运行，使用独立本机配置、SQLite 数据库、主密钥和三服务统一凭据。它只管理 `agw-` 命名空间，通过回环控制 AimiliVPN 和 3x-ui，不直接写 x-ui 数据库。

### Caddy

Caddy 作为 `caddy.service` 运行，仅承担本机管理入口反向代理。首期不申请公网证书；本机证书和信任材料独立生成，不能复用 ny 证书。UFW 将入口限制到当前 Windows 物理地址。

## 部署清单与可变规模

本机部署清单保存非秘密期望值，包括服务名、当前出口槽位数、当前 Xray 实例数、固定项目端口、构建提交和版本。秘密仍存放在权限受限的独立文件中。

状态验证比较“清单期望值”和“运行时发现值”：

- 当前清单：主连接 1、出口槽位 3、逻辑出口 4、Xray 实例 1；
- 实际值：从 AimiliVPN 状态、进程、监听端口和 systemd 读取；
- 发生偏差时报告 expected/actual，不把当前数字编译进程序或测试；
- 将来调整数量时必须重新评估 VM 内存、swap、端口范围、路由表、文件描述符和并发容量，并更新清单与验收基线。

现有项目固定端口和槽位端口分配规则保持不变。本轮不增加第五个出口，但也不新增阻止未来调整的硬编码上限。

## 数据、凭据与权限

- 为本机生成独立的 Gateway 管理员、Gateway 主密钥、AimiliVPN 控制 token、3x-ui 凭据、数据库和 Caddy 本机证书。
- 生成过程不通过命令行参数传递密码，不把秘密写入仓库、聊天或普通日志。
- 运行目录和备份目录归对应专用服务用户所有，配置与密钥使用最小文件权限。
- Gateway、x-ui、AimiliVPN 数据互不覆盖；跨服务同步只使用已定义接口。
- 安装脚本必须支持只读预检和幂等重跑；已有数据不得因普通升级被重新初始化。

## 安装、升级、备份和回滚

安装顺序固定为：基础网络与依赖 → AimiliVPN → 3x-ui/Xray → Gateway → Caddy → 主连接 → 三个出口逐个启用。

每阶段先执行预检，再创建唯一备份，再安装或升级，最后验证。备份至少覆盖该阶段会修改的二进制、配置、systemd 单元和数据库。每个组件只保留一个明确的 `previous` 或一份带清单的回滚目录，不积累无界备份。

任何阶段失败时：

1. 停止继续部署下游组件；
2. 保留失败证据和当次备份；
3. 恢复当前组件修改前状态；
4. 验证上一检查点仍可运行；
5. 不用重装或清空数据库代替根因分析。

## 网络失败处理

业务安装的硬前置条件是 VM 同时满足：局域网网关可达、公共 IP 的 TCP 443 可达、DNS 能解析、HTTPS 能完成请求。当前只有局域网网关可达，因此先按真实数据流定位：来宾路由与源地址 → 来宾防火墙 → VMnet0 桥接 → 上游网络准入。

只允许修改 VM 内或 VMware 本 VM 的配置。若证据证明上游网络拒绝第二个桥接 MAC，需要用户或网络管理员完成准入；不得通过修改 Windows 默认路由、DNS、防火墙或 v2rayN 绕过。

## 状态与验证

`status.ps1` 将报告：VM 是否存在/运行、SSH 是否可达、来宾 CPU/内存/swap/根磁盘、默认路由是否在桥接网卡、UFW 是否符合来源限制、四项 systemd 服务状态、当前部署清单期望值，以及实际 OpenVPN/Xray/逻辑出口数量。

验收分层执行：

1. VM 基础：资源、磁盘、swap、桥接、SSH、UFW、DNS、TCP 443、HTTPS；
2. 服务：四项 systemd active/enabled、重启计数、日志无新增致命错误；
3. 数据：Gateway 与 x-ui 数据库可读，配置和凭据权限符合预期；
4. 数据面：主连接后依次启用出口1至出口3，每步核对隧道、策略路由、本地代理和真实出口；
5. 控制面：四个逻辑出口均有 ready 状态，订阅包含当前部署清单声明的逻辑出口且协议隔离正确；
6. 恢复：重启 VM 后服务、数据库、隧道和受管资源恢复；
7. 宿主：v2rayN PID、系统代理和 Windows 默认路由摘要与部署前一致。

浏览器页面、订阅导入和 v2rayN 客户端连接由用户最终验收，自动验证不能替代这一步。

## 完成标准

- Docker 原型资产和专用代码已删除，其他 Docker Desktop 资源未受影响；
- VM 真实出网恢复且原因有脱敏记录；
- 四项原生 systemd 服务按首期清单运行；
- 当前四个逻辑出口完成自动数据面验证；
- 当前 OpenVPN/Xray 数量与部署清单一致，但代码没有把它们定义成永久上限；
- VM 重启恢复、数据库可读、来源限制和宿主不变性通过；
- 两个工作树分别有清晰的本地提交，不推送远程；
- 用户最终页面、订阅和 v2rayN 验收明确标记为未执行，直到用户亲自完成。
